# مصفوفة تصميم الصلاحيات ونطاق البيانات — سلسلة ERP
التاريخ: 2026-11-11
هذه مصفوفة متطلبات تصميمية. لا تثبت أن كل سياسة RLS/RPC الحالية تحققها؛ يجب فحص ذلك عند الربط الشامل.

## 1. الأدوار المرجعية
- مالك/مدير الشركة: إدارة إعدادات الشركة والفروع والمستخدمين والصلاحيات، واعتماد العمليات وفق فصل المهام.
- المدير المالي: قراءة مالية شاملة للشركة، إعداد واعتماد وترحيل قيود وسندات ضمن حدود التفويض.
- المحاسب: إعداد المستندات المالية والقيود؛ لا يعتمد أو يرحّل ما أنشأه إذا كانت سياسة فصل المهام مفعلة.
- أمين المخزن: الأصناف والمخازن والحركات والجرد والتجهيز؛ لا يطلع على الرواتب أو تفاصيل حسابات العملاء إلا ما يلزم.
- مدير المشتريات/المشتري: الموردون وطلبات وأوامر الشراء والاستلام وفواتير الموردين حسب التفويض.
- مدير المبيعات/المندوب: العملاء والطلبات والبيع والتحصيل ومتابعة المديونيات ضمن العملاء/المناطق المسندة.
- مدير الموارد البشرية: ملفات العاملين والهيكل والعقود والتوظيف والحضور والإجازات والرواتب والتقارير الحساسة.
- موظف HR/شئون موظفين: الوظائف الممنوحة فقط، مع منع اعتماد الرواتب أو كشف بيانات غير لازمة.
- الموظف: بياناته الذاتية وطلباته وقسيمة راتبه وإجازاته وفق السياسة.
- مسؤول خدمة العملاء: التذاكر والفرص والزيارات وسجل التواصل، دون بيانات رواتب أو دفاتر مالية.
- مدقق/مراجع: قراءة غير تعديل للمستندات والدفاتر والأثر وفق نطاقه.
- مدير منصة سلسلة: إدارة المنصة والتطبيقات والمعاينة المصرح بها؛ لا يكتسب تلقائيًا صلاحية التعديل في حسابات الشركات.

## 2. مصفوفة الإجراءات
| الإجراء | القاعدة | فصل المهام |
|---|---|---|
| read | يمنح حسب الدور ونطاق السجل | الحقول الحساسة تحجب حتى عند السماح بقراءة السجل |
| create | مسموح داخل الشركة والنطاق المكاني المصرح | يكتب created_by من auth.uid() خادميًا |
| update | للمسودات أو حقول مسموحة قبل الترحيل | المستند المرحل لا يعدل؛ ينشأ تصحيح/عكس |
| delete | للمسودات فقط وبصلاحية خاصة | يمنع حذف مستند مرحل أو مرجع له حركات |
| submit | يرسل المستند للمراجعة | يسجل submitter والوقت |
| approve | دور اعتماد منفصل وحدود مالية/نوع مستند | لا يعتمد المستخدم مستنده إذا فصل المهام مطلوب |
| post | ينفذ الأثر الدفتري/المخزني | RPC ذري idempotent، مع التحقق من الفترة والرصيد والحالة |
| reverse | ينشئ مستندًا عكسيًا | سبب إلزامي، موافقة، رابط للأصل، لا محو للأثر |
| export/print | نفس صلاحيات القراءة والحقول | تسجيل التصدير للبيانات الحساسة ومنع تجاوز نطاق الصفوف |
| manage_policy | مدير مخول فقط | سجل قبل/بعد وتاريخ سريان؛ لا تغيير ذاتي للصلاحيات الأعلى |
| manage_secret | خادم موثوق فقط | لا يعرض السر كاملًا في الواجهة أو السجلات |

## 3. نطاقات البيانات الإلزامية
1. **الشركة**: كل صف تشغيلي يحمل `company_id`؛ لا تقبل الشركة من العميل دون إثبات عضوية المستخدم.
2. **الفرع**: المستخدم يرى الفروع المصرح بها فقط؛ الترحيل يرفض branch_id خارج الشركة أو نطاق المستخدم.
3. **المخزن**: قراءة/صرف/استلام حسب المخازن الممنوحة؛ تحويل المخزون يتطلب صلاحية المصدر والوجهة.
4. **الموظف**: ملف الموظف ذاتي فقط؛ HR يرى الموظفين المسموحين؛ كشف الرواتب/الرقم القومي/الوثائق يحتاج صلاحية حقول حساسة.
5. **الطرف/العميل**: المندوب يرى العملاء المسندين أو نطاق منطقته، إلا إذا كان لديه صلاحية أوسع.
6. **مركز التكلفة/المشروع**: لا يرى المستخدم مشروعًا أو مركز تكلفة خارج نطاقه إلا بدور إداري.
7. **منصة سلسلة**: إدارة المنصة منفصلة عن عضوية الشركة؛ المعاينة لا تتيح تعديل بيانات الشركة.

## 4. مصفوفة RLS/RPC حسب المجال
| المجال | جداول/كيانات معروفة | سياسة SELECT | سياسة INSERT/UPDATE | DELETE | RPC/الترحيل |
|---|---|---|---|---|---|
| الأطراف والعملاء | `erp_parties`, `erp_party_classifications`, `erp_geographic_data` | عضوية الشركة ونطاق المندوب | تحقق company_id وعلاقات الشركة | تعطيل فقط عند وجود حركات | رصيد افتتاحي عبر قيد |
| المخزون | `erp_items`, `erp_inventory_movements`, `erp_stocktakes`, `erp_stocktake_lines` | شركة + مخزن + صنف | حركة من مستند معتمد | منع حذف الحركة المرحلة | ترحيل/عكس حركة ذري |
| المبيعات والمشتريات | `erp_sales_documents`, `erp_purchase_documents` وline tables | شركة + فرع + طرف | مسودة ضمن الدور | مسودة فقط | posting RPC idempotent |
| المالية | `erp_journal_entries`, `erp_journal_lines`, `erp_cash_vouchers` | شركة + نطاق حساب | مسودة فقط أو قيد تصحيح | لا حذف بعد الترحيل | اعتماد/ترحيل/عكس مع توازن |
| HR | `erp_employees`, `erp_hr_*`, `erp_payroll_runs`, `erp_payroll_lines` | عضوية نشطة + دور HR/موظف ذاتي | تحقق ربط الموظف بالشركة | أرشفة؛ لا حذف وثائق/حركات | اعتماد مسير/صرف/إقفال |
| CRM | `erp_crm_leads`, `erp_service_tickets`, `erp_service_ticket_events` | شركة + فريق/مالك التذكرة | تعيين وتحديث ضمن الفريق | إغلاق/أرشفة لا محو الحدث | SLA escalation/close |
| الأصول | `erp_fixed_assets`, `erp_asset_movements`, `erp_asset_disposals` | شركة + فرع/مركز تكلفة | مسودة حركة أصل | لا حذف بعد الرسملة | depreciation/disposal posting |
| التصنيع | BOM وأوامر الإنتاج وحركات المواد والجودة | شركة + موقع/مركز عمل | خطة/أمر ضمن الدور | مسودة فقط | issue/return/complete production |
| المقاولات | المشاريع والعقود وBOQ والمستخلصات وحركات المواد | شركة + مشروع | حسب مدير المشروع والمشتريات | لا حذف بعد اعتماد/صرف | project stock movement/certificate |
| الفاتورة الإلكترونية | `erp_einvoice_settings`, `erp_einvoice_operations` | مسؤول ضريبي وقراءة منقحة | إعدادات حسب التفويض | لا حذف أثر الإرسال | إرسال/استعلام/إلغاء عبر خادم موثوق |
| التطبيقات والتكامل | `erp_managed_apps`, API clients/logs/assets | مدير التطبيقات/المسؤول التقني | إدارة حسب دور منفصل | تعطيل/إبطال لا محو أثر | خدمة خادمية مع secrets |

## 5. متطلبات RLS الفنية
- تفعيل RLS على كل جدول يحتوي بيانات شركة أو موظف أو مستند.
- منع صلاحيات anon على الجداول الخاصة، ومنح أقل قدر من grants للأدوار.
- التحقق من عضوية الشركة النشطة، لا مجرد وجود profile أو user id.
- كل foreign key بين جداول الشركة نفسها يجب أن يتحقق من تطابق `company_id`؛ trigger أو FK مركب مناسب.
- دوال SECURITY DEFINER: search_path ثابت، صلاحية EXECUTE مقيدة، والتحقق الداخلي من هوية المستخدم والعضوية والنطاق؛ لا تعتمد على وسيط company_id فقط.
- تجنب `SECURITY DEFINER` عندما تكفي `SECURITY INVOKER`; وعزل الدوال الداخلية في schema خاص غير مكشوف عبر API.
- لا تضع service-role key أو ETA certificate أو API secret في تطبيق Flutter أو logs أو ملفات التصدير.
- اختبر محاولات IDOR: تغيير UUID لشركة أخرى، فرع آخر، مخزن آخر، موظف آخر، مستند مرحل، وRPC مع company_id مزور.
- تسجيل فشل التفويض دون تسريب البيانات أو أسرار التكامل.

## 6. متطلبات واجهة الصلاحيات
- تبويبات منفصلة: المستخدمون، أنواع المستخدمين، قوالب الصلاحيات، مصفوفة المستخدم، نطاقات الفروع والمخازن، سجل التغييرات.
- كل صف صلاحية يحدد: المجال، الشاشة، الإجراء، السماح/المنع، النطاق، حد القيمة عند اللزوم، وتاريخ السريان.
- صلاحيات حساسة مستقلة: عرض الراتب، عرض الرقم القومي، عرض الوثائق، اعتماد الرواتب، ترحيل قيد، عكس قيد، تصدير بيانات، إدارة الأسرار.
- إظهار سبب الرفض للمستخدم دون كشف تفاصيل أمنية.
- التغييرات الحساسة تحتاج تأكيدًا وتسجيلًا قبل/بعد ومنفذًا.

## 7. ما لم يُثبت بعد
- لم يتم جرد كل سياسة RLS الحالية مقابل هذه المصفوفة صفًا بصف.
- لم يتم اختبار IDOR أو تجاوز نطاق الفرع/المخزن/الموظف.
- لا يوجد في هذه الوثيقة ادعاء بأن جميع RPC الحالية idempotent أو محمية.
- يجب استخراج grants وpolicies وfunction definitions من قاعدة Supabase الفعلية أثناء مرحلة الربط، ثم تنفيذ اختبارات التفويض في الحزمة الشاملة.


## 8. مطابقة مبدئية مع الأساس الموجود في المستودع
- ملف `supabase/erp_security_membership.sql` يعرف أدوار عضوية أساسية: `owner`, `admin`, `accountant`, `manager`, `operator`, `viewer`. تُستخدم هذه كطبقة عضوية، ثم تُطبق قوالب الصلاحيات التفصيلية فوقها؛ لا يلزم توسيع قائمة أدوار العضوية لكل وظيفة فرعية.
- ملف `supabase/erp_api_integration_schema.sql` ينشئ جداول API مع RLS لكنه يتعمد عدم إنشاء سياسات وصول مباشرة لـ anon/authenticated. هذا مقصود أمنيًا؛ إدارة المفاتيح وإنشاءها وإبطالها يجب أن تمر عبر endpoint خادمي موثوق.
- دليل `docs/ERP_DEPLOYMENT_ORDER.md` يذكر وجود تنبيهات أمنية متبقية حول بعض عروض الدليل العامة ودوال SECURITY DEFINER؛ لذلك لا يُغلق محور الأمان حتى تُراجع تعريفات الدوال وEXECUTE grants وسياسات العرض العام.
- دليل النشر يعرض حالة preflight تاريخية بتاريخ 21 أكتوبر 2026؛ لا يجوز اعتبارها إثباتًا لحالة كل ترحيلات 6–11 نوفمبر أو المخطط الحالي.


## ملحق مطابقة المصفوفة مع صلاحيات Supabase الحية — 2026-11-11

### حقائق التنفيذ الحالية
- `erp_user_has_company_role` يتحقق من عضوية الشركة ودور `erp_company_members.member_role` فقط؛ لا يقرأ Permission Template أو `erp_user_permission_matrix` أو `erp_user_permissions` أو `erp_user_branch_warehouse_access`.
- سياسات `erp_user_branch_warehouse_access` تسمح للمالك/المدير/المدير العام بإدارة نطاقات المستخدم، لكن دوال حركة المخزون والتحويل والجرد والترحيل لا تستدعي فحص هذا الجدول.
- `erp_record_inventory_movement` و`erp_transfer_inventory_between_warehouses` و`erp_post_physical_stocktake` تتحقق من انتماء المخزن/الصنف للشركة وصلاحية الدور العام، لا من حق المستخدم في المخزن المحدد.
- `erp_post_sales_document` و`erp_post_purchase_document` تقبل أدوارًا أوسع من سياسات `ALL` الظاهرة على رأس المستند؛ يجب مواءمة إنشاء/تعديل المسودة مع الترحيل.
- `erp_employees` و`erp_leave_requests` و`erp_payroll_runs` تتضمن استثناءات قراءة/تعديل لمدير HR عبر `job_title`، بينما بعض إجراءات الاعتماد/الترحيل تعتمد على أدوار عضوية أخرى. لا يُمنح مدير HR كل صلاحيات الرواتب تلقائيًا.

### تصميم التفويض الملزم
1. يكون التفويض على مستوى **الفعل** لا الشاشة فقط: `read`, `create`, `edit_draft`, `submit`, `approve`, `post`, `reverse`, `export`, `download_attachment`.
2. يتحقق الخادم من الشركة والفرع والمخزن والطرف/الموظف/الخزينة قبل كل قراءة أو كتابة أو ترحيل.
3. يقرأ التحقق المركزي قالب الصلاحيات الفعلي، ويمنع أن تمنح RPC صلاحية لا تظهر في القالب أو العكس.
4. تحويل مخزني يتطلب صلاحية المصدر والوجهة معًا.
5. صلاحيات الرواتب والملفات الشخصية والتأمين والرقم القومي والجزاءات تكون مستقلة عن صلاحية HR العامة.
6. أي دالة SECURITY DEFINER تستخدم `row_security=off` يجب أن تحتوي التحقق المركزي داخل جسم الدالة؛ لا يكفي الاعتماد على RLS للجداول.

هذه فجوات مطابقة مثبتة بالـcatalog وأجسام الدوال؛ لم يتم تغيير أي سياسة أو دالة في هذه المرحلة.
