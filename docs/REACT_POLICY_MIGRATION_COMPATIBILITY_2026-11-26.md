# نقل سياسات المشروع القديم إلى واجهة React — سجل التوافق

التاريخ: 2026-11-26
الفرع: `react-parallel-preview-2026-11-25`

## ما تم نقله/تفعيله في واجهة React

- سياسات الهوية المخزنة في `erp_program_policies` تظل في قاعدة البيانات نفسها؛ لم تُنشأ قاعدة بيانات موازية ولم تُنسخ السجلات الحالية أو تُستبدل.
- أضيفت خمس مفاتيح إعدادات للشركات القائمة: لون عنوان الشاشة، خلفية عناوين الأعمدة، لون نص عناوين الأعمدة، لون الصفوف المتبادلة، ولون الصف عند المرور.
- واجهة React تقرأ هذه القيم من سياسات الشركة النشطة وتحوّلها إلى CSS custom properties.
- القيم الافتراضية: عنوان الشاشة `#3E007D`، رأس الجدول `#FFA015`، نص الرأس `#241735`، الصف المتبادل `#FAF8FC`، والمرور `#F5EFFB`.
- أُبقيت سجلات السياسات السابقة كما هي؛ الترحيل يستخدم `ON CONFLICT DO NOTHING` ولا يكتب فوق قيمة سبق أن ضبطها المستخدم.

## سياسات قديمة قابلة لإعادة الاستخدام

قيم الهوية، اللغة، اسم البرنامج، الشعار، قواعد الشركة/الفروع، وسياسات التشغيل والتكويد يمكن أن تبقى بيانات مشتركة في Supabase. شاشة سياسات React الحالية تقرأ وتحرر سجل `erp_program_policies`، لكن لا يعني ذلك أن كل سياسة تشغيلية أو كل إعداد Flutter أصبح له أثر تنفيذي تلقائيًا في React.

## تعارضات وفروق تقنية مؤكدة

1. **Flutter ThemeData مقابل React/CSS:** لا يمكن نقل `ThemeData` أو `InputDecorationTheme` أو `DataTableThemeData` أو Widgets كما هي. تُحوّل القيم إلى CSS variables ومكونات React، وقد تحتاج كل شاشة مخصصة إلى adapter.
2. **Silsila Studio القديم:** ملفات تعريف Studio وتطبيقها عبر `ErpScreenLayoutRuntime` و`ErpScreenFrame` مرتبطة بشجرة Widgets في Flutter. لا تعمل مباشرة في React؛ يلزم runtime مستقل لـReact قبل اعتبار تحكم Studio القديم منقولًا.
3. **قياسات القوائم والتفاعل:** معيار ارتفاع الحقل/الصف 40px قابل للتطبيق في CSS، لكن حد مساحة اللمس الموصى به على الهاتف قد يتطلب هدفًا تفاعليًا أكبر من 40px حتى لو ظل الشكل المرئي 40px.
4. **المسافة بين الأعمدة:** قيمة 5px كانت مواصفة أقدم، وقد تم تجاوزها بقرار أحدث بتاريخ 2026-11-21 يفرض 2px في `ui_layout_standard`. القيمة المعتمدة حاليًا هي 2px؛ يجب أن تعتمدها جداول React، ولا يجوز إعادة 5px.
5. **عناوين الحقول بجوارها:** React يمكنه دعمها عبر مكونات النماذج وCSS، لكنها ليست نتيجة تلقائية لنقل `InputDecoration.labelText` أو إعداد Flutter؛ بعض النماذج تحتاج إعادة تركيب.
6. **صلاحيات/RLS:** سياسات Supabase وقيود company/branch/warehouse قابلة للمشاركة لأنها في قاعدة البيانات، لكن يجب أن يظل React ملتزمًا بها عبر استعلامات آمنة وفحوص صلاحيات واجهة المستخدم. إخفاء زر وحده ليس حماية.
7. **تخصيصات Flutter المحلية:** أي قيمة محفوظة محليًا في SharedPreferences أو مرتبطة بسياق Flutter لا تنتقل إلى متصفح React دون طبقة تحويل وتخزين صريحة.

## حدود التنفيذ الحالي

- تم توصيل رموز الألوان الخمسة في React بقراءة سياسات Supabase، وإضافة ترحيل SQL idempotent.
- لم يتم تشغيل migration على قاعدة الإنتاج، ولم يتم تعديل بيانات الشركة أو تفعيل تغيير في الإنتاج.
- لم يتم الادعاء بأن كل سياسات التشغيل والتكويد القديمة أصبحت مطبقة في React؛ بعضها بيانات مشتركة بالفعل، وبعضها يحتاج تنفيذًا خاصًا بالتقنية الجديدة.
- لم يتم نقل/تفعيل محرر Studio القديم داخل React في هذه الدفعة.


## جرد سياسات المشروع القديم وموقف React

### سياسات تشغيلية وإدارية محفوظة في `erp_program_policies`
تشمل، ضمن المفاتيح المعروفة في migrations: السنة المالية، تقييم وجرد المخزون، الإهلاك، منع تكرار الأصناف، ضوابط التسويات، أساس تقييم الجرد، مدة البيع/الشراء/التحويل والعروض في سوق التجار، تعيين مندوب افتراضي للعميل، سياسة السعر الافتراضية، تعديل مستند مستخدم آخر، ترحيل عجز العميل للفاتورة، تدقيق فاتورة البيع، تخطي عرض السعر/أمر البيع/أمر التوريد/أمر الشراء، فروق مكافآت المورد، اشتراط الرقم القومي، وسياسة سجل مولد الأكواد.
هذه القيم محفوظة على مستوى الشركة ويستطيع React عرضها وتعديل قيمة السياسة وحالة تفعيلها ونطاق تطبيقها. لكن أثرها التشغيلي يأتي من triggers/RPC وخدمات المجال في Supabase؛ مجرد ظهورها في React لا يثبت أن كل شاشة React تستخدم القيمة أو تحترمها.

### سياسات التكويد
- توجد 67 عائلة أكواد مركزية بحسب تدقيق 2026-11-11، إضافة إلى سياسات مخصصة للعملاء، الجغرافيا، فئات الأصناف، البراندات، الأصناف، الموظفين، المستخدمين، الفروع، المخازن/المواقع، الحسابات، الخزائن، المستندات، HR، CRM، التصنيع والمقاولات والخدمات.
- مولدات الأكواد الأساسية موجودة في Supabase وتظل صالحة تقنيًا مع React لأنها تعمل على مستوى قاعدة البيانات.
- واجهة React الحالية تعرض سياسة التكويد في جدول السياسات وتحرر `policy_value` كنص/JSON عام؛ لا يوجد بعد محرر بصري متخصص لكل نوع كود أو معاينة موحدة تربط كل حقل بالـgenerator المقابل.
- يجب عدم السماح للواجهة الجديدة بإظهار قيمة قابلة للتعديل لا يقرأها المولد الفعلي، أو بعرض معاينة كود عامة لا تطابق trigger المتخصص.

### الهوية البصرية
أضيفت مفاتيح `Idn013` إلى `Idn017` للألوان الخمسة. محرر السياسة في React أصبح يعرض منتقي لون ويدقق صيغة HEX ذات 6 خانات لهذه المفاتيح. بقية مفاتيح الهوية القديمة تظل في نفس الجدول دون تغيير.

### Silsila Studio
جداول `erp_studio_designs`, `erp_studio_design_versions`, `erp_studio_layout_profiles` وسجل التدقيق وRPCs القديمة قابلة للاحتفاظ بها في Supabase. لكن محرر Flutter/Runtime لا ينتقل إلى React تلقائيًا؛ لا يوجد في هذه الدفعة محرر React مكافئ يقرأ مخططات Studio وينفذها ويعتمد نسخها المنشورة. لذلك هذا **تعارض تنفيذ/Runtime وليس تعارض تخزين**.

### قرارات قياس الواجهة المعتمدة
- ارتفاع الصف والحقل: 40px.
- المسافة بين الأعمدة: 2px (قرار 2026-11-21، ويتقدم على القيمة القديمة 5px).
- ارتفاع هدف اللمس في القوائم/الخيارات قد يحتاج 48px على الأجهزة اللمسية؛ لا تخلط بين مساحة اللمس وارتفاع الحقل المرئي 40px.
- RTL، Tajawal، عناوين الحقول بجوار المدخل، والهيدر المحمول المدمج تحتاج مطابقة مكونات React فعليًا، لا مجرد نسخ قيم Theme Flutter.

## ما تم تغييره بعد جرد الواجهة

- أضيف منتقي لون مباشر لسياسات الألوان الخمس مع حقل HEX قابل للتحرير ومعاينة.
- تظهر بيانات تعريف السياسة داخل المحرر: كود السياسة والمفتاح التقني.
- يُرفض الحفظ إذا كانت قيمة لون من المفاتيح الخمسة لا تطابق `#RRGGBB`.
- لم نضف سياسة تشغيلية أو كود جديدًا يدويًا؛ تم الحفاظ على الكتالوج القديم كما هو، وأضيفت فقط مفاتيح الهوية الخمسة.
