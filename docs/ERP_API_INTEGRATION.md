# تكامل API لنظام سلسلة ERP

## الحالة الحالية
- ملف `lib/erp/services/erp_api_integration.dart` يحتوي نماذج إعداد التكامل وقائمة أولية لمسارات API المقترحة.
- ملف `supabase/erp_api_integration_schema.sql` يعرّف سجل أنظمة الربط وسجل الطلبات.
- المسارات الموجودة في الكتالوج تصميم مبدئي وليست endpoints عاملة بعد.
- جداول ERP مقفلة بسياسات RLS؛ لم يتم فتح وصول مباشر للمتصفح أو المستخدم المجهول.

## خطوات التشغيل قبل ربط أي برنامج خارجي
1. تطبيق `supabase/erp_schema.sql` على مشروع Supabase المقصود بعد مراجعته.
2. تطبيق `supabase/erp_operations_schema.sql` بعد نجاح المخطط الأساسي.
3. تطبيق `supabase/erp_master_data_schema.sql` لإضافة وحدات الصنف البديلة وجهات اتصال الأطراف وقوائم أسعار الشراء والبيع وربطها بالأطراف.
4. تطبيق `supabase/erp_api_integration_schema.sql` عند بدء إعداد سجل تكامل API.
5. مراجعة صلاحيات الشركة والفرع والمستخدم، ثم كتابة سياسات RLS دقيقة قبل السماح بقراءة أو تعديل البيانات.
6. بناء API خلفي موثوق (مثل Edge Functions أو خدمة خلفية منفصلة) للتحقق من هوية العميل، نطاق الصلاحيات، الشركة والفرع، حدود الطلبات، ومنع تكرار الطلبات.
7. توليد سر API عشوائي قوي على الخادم؛ عرض السر مرة واحدة فقط وتخزين hash لا النص الأصلي.
8. حفظ أسرار الخدمة في متغيرات بيئة/مدير أسرار للخادم فقط، وعدم تضمين `service_role` أو مفاتيح سرية في تطبيق Flutter أو مستودع Git.
10. تسجيل request ID والطريق والنتيجة والمدة والأخطاء الآمنة، دون تسجيل Authorization headers أو كلمات المرور أو أسرار API.
11. تفعيل HTTPS، وتحديد scopes لكل عميل، وسياسة تدوير/إلغاء المفاتيح، وحدود معدل الطلبات، وقائمة IP عند الحاجة.
12. توثيق API بإصدار واضح وعقود JSON، ثم إضافة اختبارات تكامل بعد اكتمال التطوير وفق خطة المشروع.

## إضافات البيانات الأساسية
- `erp_item_units`: وحدات بديلة ومعامل تحويل وباركود للصنف.
- `erp_party_contacts`: أكثر من جهة اتصال للمورد أو العميل مع جهة اتصال أساسية.
- `erp_price_lists` و`erp_price_list_lines`: قوائم أسعار شراء/بيع وأسعار حسب حد الكمية وفترة السريان.
- `erp_party_price_lists`: ربط قائمة سعر بعميل أو مورد.
- جميع الجداول الجديدة مفعّل عليها RLS بلا سياسات سماح؛ لا تُفتح مباشرة قبل تطبيق تفويض الشركة والتحقق من تطابق الشركة بين السجلات في الخادم.

## اختبار ومراجعة الحركات
- شاشة اختبار ومراجعة الحركات تدعم اختيار جميع الحركات أو مجال محدد، والفحص من بداية النظام أو شهر محدد أو نطاق تاريخي.
- ملف supabase/erp_movement_audit_schema.sql يتضمن الدالة القرائية public.erp_audit_movements(company_id, start_date, end_date, area) لإرجاع تقرير بالمشكلات التي يمكن اكتشافها في المخطط الحالي: مستندات مبيعات/مشتريات مرحّلة بلا سطور، مستندات مرحّلة بلا قيد يومية مرتبط عبر source_id، قيود يومية مرحّلة بلا سطور أو غير متوازنة، وعدم تطابق الشركة في حركة المخزون والصنف.
- يجب تطبيق erp_schema.sql وerp_operations_schema.sql أولًا ثم مراجعة وتطبيق erp_movement_audit_schema.sql يدويًا في SQL Editor.
- الدالة للقراءة فقط ولا تصلح المستند الأصلي تلقائيًا. زر ضبط الحركة في الواجهة يسجل ملاحظة مراجعة محلية فقط إلى أن يتم بناء واجهة تعديل آمنة تربط كل نتيجة بالمستند الحقيقي وخدمة خلفية ذات صلاحيات محددة.
- الدالة ممنوعة عن anon وauthenticated ومسموح بها لـ service_role فقط؛ استدعاؤها يجب أن يكون من خادم موثوق، ولا يجوز تضمين مفتاح service_role في تطبيق Flutter.
- ما زالت مراجعة العملاء والخزائن والبنوك والموظفين والتسويات الشاملة تحتاج جداول حركاتها الفعلية وقواعدها قبل إضافة فحوصات تشغيلية لها. بيانات العينة في شاشة Flutter ليست نتائج تدقيق فعلية.


## الموارد البشرية والحضور والبصمة
- تمت إضافة واجهتي `lib/erp/screens/hr_attendance_rules_screen.dart` لقواعد الورديات والحضور والانصراف، وواجهة أجهزة البصمة المتعددة عبر IP أو USB.
- تمت إضافة `supabase/erp_hr_attendance_schema.sql` ويشمل تعريف الورديات وقواعد السماح والتأخير ونسيان البصمة والغياب والإجازات، وتنسيب الموظفين، وتعريف أجهزة البصمة، وسجل أحداث الحضور الخام مع منع التكرار حسب الجهاز ومعرف الحدث المصدر.
- يجب مراجعة الملف ثم تطبيقه يدويًا بعد `supabase/erp_schema.sql` في مشروع Supabase المقصود. جداول الموارد البشرية مفعّل عليها RLS بلا سياسات سماح للعميل؛ يلزم تصميم صلاحيات الشركة والفرع قبل تشغيلها.
- أيقونات أزرار الوصول السريع في لوحة ERP أصبحت برتقالية `#FFA015` مع بقاء نص الزر أبيض.
- الواجهات الجديدة حاليًا مسودات تفاعلية محلية وليست متصلة بقاعدة البيانات. لا تُعرض حالة جهاز «متصل» ولا يتم الادعاء بسحب حركات فعلية دون موصل بروتوكول ناجح. ربط IP يعتمد على نوع جهاز البصمة وبروتوكوله، وUSB يتطلب دعمًا أصليًا على النظام المستهدف أو خدمة وسيطة.
- قبل اعتماد قواعد التأخير يجب ضبط الشرائح الخمس لتكون متتابعة بلا فجوات أو تداخل، ومراجعة كيفية تمثيل قيمة الدقيقة (مبلغ مالي أو معامل احتساب) مع سياسة الرواتب المعتمدة. بيانات الموظفين/الأقسام والفروع التجريبية لا تمثل سجلات فعلية.


## شجرة الحسابات وأرصدة دفتر الأستاذ
- أضيف الملف `supabase/erp_account_tree_metrics.sql` بعد `supabase/erp_schema.sql` لإنشاء عرضين للقراءة: `erp_account_ledger_totals` لإجماليات كل حساب، و`erp_account_tree_metrics` لتجميع الحسابات التابعة بصورة هرمية.
- الأرصدة تعتمد على القيود ذات الحالة `posted` فقط؛ القيود المسودة أو المعكوسة لا تدخل في الإجمالي. يوفر العرض الرصيد المدين والدائن والصافي، وعدد الحركات، وعدد الحسابات التابعة، ونسبة الرصيد إلى إجمالي القيم المطلقة للحسابات القابلة للترحيل.
- العرضان يستخدمان `security_invoker = true` حتى لا يتجاوزا سياسات RLS للجداول الأساسية. لا تمنح هذه الإضافة أي صلاحيات تلقائيًا، ويجب إعداد سياسات الشركة والفرع قبل إتاحة القراءة للمستخدمين.
- ملف SQL أُضيف إلى المستودع فقط ولم يُنفذ على مشروع Supabase. كما أن واجهة الشجرة الحالية ما زالت تعرض بيانات توضيحية؛ لم يتم ربطها بالعرضين بعد.


## طبقة خدمة شجرة الحسابات
- أضيف `lib/erp/services/erp_accounts_repository.dart` لقراءة مؤشرات الحسابات من `erp_account_tree_metrics`، وإنشاء الحسابات وتعديلها وتعطيلها بدل الحذف، مع اشتراط تمرير `companyId` صراحة.
- أضيف `supabase/erp_account_integrity.sql` للتحقق على قاعدة البيانات من أن الحساب الأب تابع للشركة نفسها، ومنع إضافة أبناء إلى حساب قابل للترحيل، ومنع تحويل حساب له أبناء إلى حساب قابل للترحيل.
- لم يتم ربط شاشة الشجرة بهذه الخدمة بعد؛ فهي ما زالت تستخدم الشجرة التوضيحية. لم يتم تشغيل ملفات SQL على Supabase، كما أن جداول ERP الحالية تعمل بسياسات RLS مغلقة حتى تُضاف سياسات تفويض الشركة والمستخدم. لذلك لن تعمل القراءة/الكتابة الفعلية من التطبيق حتى تهيئة Supabase وتطبيق المخططات والسياسات المناسبة.


## شاشة شجرة الحسابات المرتبطة بالبيانات
- أصبحت قائمة `شجرة الحسابات` تفتح `lib/erp/screens/erp_accounts_screen.dart` بدل الشجرة الثابتة التوضيحية.
- الشاشة تطلب معرّف الشركة (UUID)، وتقرأ الحسابات ومؤشرات دفتر الأستاذ من `erp_account_tree_metrics`، وتدعم البحث وتصفية الحسابات النشطة وإضافة حساب جديد.
- لا تضع معرّفًا افتراضيًا للشركة ولا تتجاوز RLS. إذا كانت سياسات الوصول أو مخططات SQL غير مطبقة، ستعرض الشاشة الخطأ الوارد من Supabase.
- شاشة التحرير الشامل للحسابات وتغيير الحساب الأب والتكامل الكامل مع القيود لا تزال ضمن العمل اللاحق.


## تحرير شجرة الحسابات وتغيير الحساب الأب
- تدعم `lib/erp/screens/erp_accounts_screen.dart` إضافة الحساب وتعديل الكود والاسم والنوع وطبيعة الرصيد والأب وقابلية الترحيل وحالة النشاط.
- تتحقق `lib/erp/services/erp_accounts_repository.dart` من وجود الأب في الشركة نفسها، ومن عدم كون الأب حسابًا تحليليًا قابلًا للترحيل، ومن عدم نقل الحساب إلى أحد أحفاده.
- الملف `supabase/erp_account_integrity.sql` يتضمن فحصًا على مستوى قاعدة البيانات لمنع الدورات الهرمية، بالإضافة إلى ضوابط الحساب الأب والحسابات التحليلية.
- التعديلات حُفظت في المستودع فقط. لم تُطبق ملفات SQL على Supabase، ولم تُشغّل اختبارات أو عملية بناء؛ لذلك لا يُعد التكامل مُشغّلًا حتى تُطبق المخططات وتُضبط سياسات RLS.


## قيود اليومية
- أضيفت شاشة `lib/erp/screens/erp_journal_entries_screen.dart` وربطت بخيار «قيود اليومية» في لوحة ERP.
- أضيفت خدمة `lib/erp/services/erp_journal_repository.dart` لقراءة القيود والحسابات القابلة للترحيل وحفظ المسودات وطلب ترحيلها.
- أضيف `supabase/erp_journal_workflow.sql` لدالتي حفظ المسودة والترحيل. تتحقق الدوال من الشركة والحسابات والفترة المالية وتوازن المدين والدائن قبل الترحيل، وتعملان مع سياسات RLS ولا تتجاوزانها.
- لم يُطبق SQL على Supabase، ولم تُشغّل اختبارات أو عملية بناء. تحرير المسودات القائمة والعكس المحاسبي والاعتماد متعدد المستويات ما زالت أعمالًا لاحقة.

## الأستاذ العام وميزان المراجعة وحركة الحساب
- أضيف `supabase/erp_ledger_reports.sql` لإنشاء العرض `erp_general_ledger` ودالة `erp_get_trial_balance`.
- الأستاذ العام وحركة الحساب يعرضان سطور القيود المرحلة فقط، ويمكن تحديد تاريخ بداية ونهاية، وتصفية حركة الحساب بمعرّف الحساب.
- ميزان المراجعة يجمع المدين والدائن لكل حساب داخل الشركة، مع نطاق تاريخي اختياري، ويستبعد المسودات والقيود المعكوسة.
- أضيفت خدمة `lib/erp/services/erp_ledger_reports_repository.dart` وشاشة `lib/erp/screens/erp_ledger_reports_screen.dart` وربطت خيارات «ميزان المراجعة» و«الأستاذ العام» و«حركة حساب» في لوحة ERP.
- ملف SQL موجود في المستودع فقط ولم يُطبق على Supabase. يجب تطبيق المخطط الأساسي وتدفق القيود أولًا، ثم ملف التقارير، وبعدها إعداد RLS المناسبة. لم تُشغّل اختبارات أو عملية بناء.
- التقارير حاليًا قراءة فقط؛ لم يتم بعد إضافة أرصدة افتتاحية أو قوائم مالية كاملة أو ترحيل آلي من فواتير البيع والشراء.

## استكمال تحرير قيود اليومية
- أصبحت شاشة قيود اليومية تدعم عرض تفاصيل سطور القيد المحفوظ، وتحرير القيد ما دام في حالة `draft`، مع إعادة حفظ السطور من خلال دالة المعاملة `erp_save_journal_draft`.
- لا يظهر زر التحرير للقيود المرحلة أو المعكوسة؛ هذه الحالات تحتاج إجراء عكس محاسبي منفصلًا يحفظ الأثر التاريخي ولا يعدل القيد المرحّل.
- تعتمد قراءة السطور على علاقة `erp_accounts` في Supabase، ولذلك يلزم أن تكون صلاحيات قراءة الحسابات والقيود والسطور مضبوطة للمستخدم والشركة.

## العكس المحاسبي للقيود المرحلة
- أضيف `supabase/erp_journal_reversal.sql` والدالة `erp_reverse_journal_entry` لإنشاء قيد عكس جديد بتاريخ وسبب إلزاميين، بعكس مبالغ المدين والدائن لكل سطر.
- يحتفظ النظام بالقيد الأصلي المرحّل ويضيف قيدًا مرحّلًا منفصلًا مرتبطًا به من خلال `source_type = 'reversal'` و`source_id`. تمنع الدالة إنشاء عكس ثانٍ لنفس القيد.
- أضيفت دالة `reverseEntry` في `ErpJournalRepository` وزر «إنشاء قيد عكس» للقيود المرحلة، مع طلب سبب العكس وتاريخه.
- يجب تطبيق ملفات SQL بالترتيب: `erp_schema.sql` ثم `erp_journal_workflow.sql` ثم `erp_ledger_reports.sql` ثم `erp_journal_reversal.sql`. هذه الملفات لم تُطبّق على قاعدة Supabase حتى الآن.
- الدوال تستخدم `security invoker`؛ لذلك يجب إعداد RLS وسياسات إدخال وقراءة وتحديث مناسبة للمستخدمين والشركة قبل التجربة. لم تُشغّل اختبارات أو عملية بناء.

## ربط صلاحيات الشركات (RLS) قبل الاختبار
- أضيف `supabase/erp_security_membership.sql` لإنشاء جدول عضويات الشركات `erp_company_members` والأدوار `owner`, `admin`, `accountant`, `manager`, `operator`, `viewer`، وسياسات RLS لجداول ERP والقيود.
- لا يُفتح الوصول العام إلى البيانات. يجب إضافة مستخدم Supabase Auth إلى الشركة بدور مناسب قبل أن يتمكن من القراءة أو الحفظ.
- بعد إنشاء سجل الشركة من SQL Editor أو من مسار إداري موثوق، أضف عضوية المستخدم الأول يدويًا باستخدام UUID الخاص به من Authentication → Users. مثال توضيحي فقط، استبدل المعرفات بالقيم الفعلية:
  `insert into public.erp_company_members (company_id, user_id, member_role) values ('COMPANY-UUID', 'AUTH-USER-UUID', 'owner');`
  يجب إدخال UUID صالح بدل النصين التوضيحيين. لا تضع مفتاح `service_role` داخل التطبيق.
- سياسة إدخال الشركات من تطبيق العميل مغلقة عمدًا؛ إنشاء الشركة الأولى وتعيين مالكها خطوة إدارية منفصلة.
- يضيف ملف الأمان أيضًا حارسًا يمنع تعديل رأس القيد بعد ترحيله. لتصحيح قيد مرحّل يجب إنشاء قيد عكس بدل تغيير التاريخ أو البيان أو السطور الأصلية.
- ترتيب التطبيق المقترح: `erp_schema.sql` ثم `erp_account_integrity.sql` ثم `erp_account_tree_metrics.sql` ثم `erp_journal_workflow.sql` ثم `erp_security_membership.sql` ثم `erp_ledger_reports.sql` ثم `erp_journal_reversal.sql` ثم `erp_movement_audit.sql`.
- راجع سياسة الشركة وأدوار المستخدمين قبل التنفيذ على بيانات حقيقية. لا تشغّل هذه الملفات على قاعدة إنتاج تحتوي بيانات قائمة دون مراجعة المخطط والنسخ الاحتياطي.
