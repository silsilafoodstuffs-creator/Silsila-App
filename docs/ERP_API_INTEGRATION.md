# تكامل API لنظام سلسلة ERP

## الحالة الحالية
- ملف `lib/erp/services/erp_api_integration.dart` يحتوي نماذج إعداد التكامل وقائمة أولية لمسارات API المقترحة.
- ملف `supabase/erp_api_integration_schema.sql` يعرّف سجل أنظمة الربط وسجل الطلبات.
- المسارات الموجودة في الكتالوج تصميم مبدئي وليست endpoints عاملة بعد.
- جداول ERP مقفلة بسياسات RLS؛ لم يتم فتح وصول مباشر للمتصفح أو المستخدم المجهول.

## خطوات التشغيل قبل ربط أي برنامج خارجي
1. تطبيق `supabase/erp_schema.sql` على مشروع Supabase المقصود بعد مراجعته.
2. تطبيق `supabase/erp_operations_schema.sql` بعد نجاح المخطط الأساسي.
3. تطبيق `supabase/erp_master_data_schema.sql` لإضافة وحدات الصنف البديلة وجهات اتصال الأطراف وقوائم أسعار الشراء والبيع وربطها بالأطراف.
4. تطبيق `supabase/erp_api_integration_schema.sql` عند بدء إعداد سجل تكامل API.
5. مراجعة صلاحيات الشركة والفرع والمستخدم، ثم كتابة سياسات RLS دقيقة قبل السماح بقراءة أو تعديل البيانات.
6. بناء API خلفي موثوق (مثل Edge Functions أو خدمة خلفية منفصلة) للتحقق من هوية العميل، نطاق الصلاحيات، الشركة والفرع، حدود الطلبات، ومنع تكرار الطلبات.
7. توليد سر API عشوائي قوي على الخادم؛ عرض السر مرة واحدة فقط وتخزين hash لا النص الأصلي.
8. حفظ أسرار الخدمة في متغيرات بيئة/مدير أسرار للخادم فقط، وعدم تضمين `service_role` أو مفاتيح سرية في تطبيق Flutter أو مستودع Git.
10. تسجيل request ID والطريق والنتيجة والمدة والأخطاء الآمنة، دون تسجيل Authorization headers أو كلمات المرور أو أسرار API.
11. تفعيل HTTPS، وتحديد scopes لكل عميل، وسياسة تدوير/إلغاء المفاتيح، وحدود معدل الطلبات، وقائمة IP عند الحاجة.
12. توثيق API بإصدار واضح وعقود JSON، ثم إضافة اختبارات تكامل بعد اكتمال التطوير وفق خطة المشروع.

## إضافات البيانات الأساسية
- `erp_item_units`: وحدات بديلة ومعامل تحويل وباركود للصنف.
- `erp_party_contacts`: أكثر من جهة اتصال للمورد أو العميل مع جهة اتصال أساسية.
- `erp_price_lists` و`erp_price_list_lines`: قوائم أسعار شراء/بيع وأسعار حسب حد الكمية وفترة السريان.
- `erp_party_price_lists`: ربط قائمة سعر بعميل أو مورد.
- جميع الجداول الجديدة مفعّل عليها RLS بلا سياسات سماح؛ لا تُفتح مباشرة قبل تطبيق تفويض الشركة والتحقق من تطابق الشركة بين السجلات في الخادم.

## المسارات المقترحة
| Method | Path | Scope |
|---|---|---|
| GET | `/v1/company` | `company:read` |
| GET | `/v1/items` | `items:read` |
| GET | `/v1/customers` | `customers:read` |
| GET | `/v1/suppliers` | `suppliers:read` |
| GET | `/v1/inventory/balances` | `inventory:read` |
| POST | `/v1/orders` | `orders:write` |

لا تنفّذ أي مسار من هذه المسارات عمليات فعلية حتى يتم بناء الخادم والتحقق من الصلاحيات وربطه بقاعدة البيانات.

## اختبار ومراجعة الحركات
- شاشة اختبار ومراجعة الحركات تدعم اختيار جميع الحركات أو مجال محدد، والفحص من بداية النظام أو شهر محدد أو نطاق تاريخي.
- ملف supabase/erp_movement_audit_schema.sql يتضمن الدالة القرائية public.erp_audit_movements(company_id, start_date, end_date, area) لإرجاع تقرير بالمشكلات التي يمكن اكتشافها في المخطط الحالي: مستندات مبيعات/مشتريات مرحّلة بلا سطور، مستندات مرحّلة بلا قيد يومية مرتبط عبر source_id، قيود يومية مرحّلة بلا سطور أو غير متوازنة، وعدم تطابق الشركة في حركة المخزون والصنف.
- يجب تطبيق erp_schema.sql وerp_operations_schema.sql أولًا ثم مراجعة وتطبيق erp_movement_audit_schema.sql يدويًا في SQL Editor.
- الدالة للقراءة فقط ولا تصلح المستند الأصلي تلقائيًا. زر ضبط الحركة في الواجهة يسجل ملاحظة مراجعة محلية فقط إلى أن يتم بناء واجهة تعديل آمنة تربط كل نتيجة بالمستند الحقيقي وخدمة خلفية ذات صلاحيات محددة.
- الدالة ممنوعة عن anon وauthenticated ومسموح بها لـ service_role فقط؛ استدعاؤها يجب أن يكون من خادم موثوق، ولا يجوز تضمين مفتاح service_role في تطبيق Flutter.
- ما زالت مراجعة العملاء والخزائن والبنوك والموظفين والتسويات الشاملة تحتاج جداول حركاتها الفعلية وقواعدها قبل إضافة فحوصات تشغيلية لها. بيانات العينة في شاشة Flutter ليست نتائج تدقيق فعلية.


## الموارد البشرية والحضور والبصمة
- تمت إضافة واجهتي `lib/erp/screens/hr_attendance_rules_screen.dart` لقواعد الورديات والحضور والانصراف، وواجهة أجهزة البصمة المتعددة عبر IP أو USB.
- تمت إضافة `supabase/erp_hr_attendance_schema.sql` ويشمل تعريف الورديات وقواعد السماح والتأخير ونسيان البصمة والغياب والإجازات، وتنسيب الموظفين، وتعريف أجهزة البصمة، وسجل أحداث الحضور الخام مع منع التكرار حسب الجهاز ومعرف الحدث المصدر.
- يجب مراجعة الملف ثم تطبيقه يدويًا بعد `supabase/erp_schema.sql` في مشروع Supabase المقصود. جداول الموارد البشرية مفعّل عليها RLS بلا سياسات سماح للعميل؛ يلزم تصميم صلاحيات الشركة والفرع قبل تشغيلها.
- أيقونات أزرار الوصول السريع في لوحة ERP أصبحت برتقالية `#FFA015` مع بقاء نص الزر أبيض.
- الواجهات الجديدة حاليًا مسودات تفاعلية محلية وليست متصلة بقاعدة البيانات. لا تُعرض حالة جهاز «متصل» ولا يتم الادعاء بسحب حركات فعلية دون موصل بروتوكول ناجح. ربط IP يعتمد على نوع جهاز البصمة وبروتوكوله، وUSB يتطلب دعمًا أصليًا على النظام المستهدف أو خدمة وسيطة.
- قبل اعتماد قواعد التأخير يجب ضبط الشرائح الخمس لتكون متتابعة بلا فجوات أو تداخل، ومراجعة كيفية تمثيل قيمة الدقيقة (مبلغ مالي أو معامل احتساب) مع سياسة الرواتب المعتمدة. بيانات الموظفين/الأقسام والفروع التجريبية لا تمثل سجلات فعلية.


## شجرة الحسابات وأرصدة دفتر الأستاذ
- أضيف الملف `supabase/erp_account_tree_metrics.sql` بعد `supabase/erp_schema.sql` لإنشاء عرضين للقراءة: `erp_account_ledger_totals` لإجماليات كل حساب، و`erp_account_tree_metrics` لتجميع الحسابات التابعة بصورة هرمية.
- الأرصدة تعتمد على القيود ذات الحالة `posted` فقط؛ القيود المسودة أو المعكوسة لا تدخل في الإجمالي. يوفر العرض الرصيد المدين والدائن والصافي، وعدد الحركات، وعدد الحسابات التابعة، ونسبة الرصيد إلى إجمالي القيم المطلقة للحسابات القابلة للترحيل.
- العرضان يستخدمان `security_invoker = true` حتى لا يتجاوزا سياسات RLS للجداول الأساسية. لا تمنح هذه الإضافة أي صلاحيات تلقائيًا، ويجب إعداد سياسات الشركة والفرع قبل إتاحة القراءة للمستخدمين.
- ملف SQL أُضيف إلى المستودع فقط ولم يُنفذ على مشروع Supabase. كما أن واجهة الشجرة الحالية ما زالت تعرض بيانات توضيحية؛ لم يتم ربطها بالعرضين بعد.
