# تكامل API لنظام سلسلة ERP

## الحالة الحالية
- ملف `lib/erp/services/erp_api_integration.dart` يحتوي نماذج إعداد التكامل وقائمة أولية لمسارات API المقترحة.
- ملف `supabase/erp_api_integration_schema.sql` يعرّف سجل أنظمة الربط وسجل الطلبات.
- المسارات الموجودة في الكتالوج تصميم مبدئي وليست endpoints عاملة بعد.
- جداول ERP مقفلة بسياسات RLS؛ لم يتم فتح وصول مباشر للمتصفح أو المستخدم المجهول.

## خطوات التشغيل قبل ربط أي برنامج خارجي
1. تطبيق `supabase/erp_schema.sql` على مشروع Supabase المقصود بعد مراجعته.
2. تطبيق `supabase/erp_operations_schema.sql` بعد نجاح المخطط الأساسي.
3. مراجعة صلاحيات الشركة والفرع والمستخدم، ثم كتابة سياسات RLS دقيقة قبل السماح بقراءة أو تعديل البيانات.
4. بناء API خلفي موثوق (مثل Edge Functions أو خدمة خلفية منفصلة) للتحقق من هوية العميل، نطاق الصلاحيات، الشركة والفرع، حدود الطلبات، ومنع تكرار الطلبات.
5. توليد سر API عشوائي قوي على الخادم؛ عرض السر مرة واحدة فقط وتخزين hash لا النص الأصلي.
6. حفظ أسرار الخدمة في متغيرات بيئة/مدير أسرار للخادم فقط، وعدم تضمين `service_role` أو مفاتيح سرية في تطبيق Flutter أو مستودع Git.
7. تسجيل request ID والطريق والنتيجة والمدة والأخطاء الآمنة، دون تسجيل Authorization headers أو كلمات المرور أو أسرار API.
8. تفعيل HTTPS، وتحديد scopes لكل عميل، وسياسة تدوير/إلغاء المفاتيح، وحدود معدل الطلبات، وقائمة IP عند الحاجة.
9. توثيق API بإصدار واضح وعقود JSON، ثم إضافة اختبارات تكامل بعد اكتمال التطوير وفق خطة المشروع.

## المسارات المقترحة
| Method | Path | Scope |
|---|---|---|
| GET | `/v1/company` | `company:read` |
| GET | `/v1/items` | `items:read` |
| GET | `/v1/customers` | `customers:read` |
| GET | `/v1/suppliers` | `suppliers:read` |
| GET | `/v1/inventory/balances` | `inventory:read` |
| POST | `/v1/orders` | `orders:write` |

لا تنفّذ أي مسار من هذه المسارات عمليات فعلية حتى يتم بناء الخادم والتحقق من الصلاحيات وربطه بقاعدة البيانات.
