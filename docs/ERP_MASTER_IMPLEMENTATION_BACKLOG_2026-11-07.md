## 1. قواعد هذا الحصر
- وجود ملف شاشة أو مسار أو جدول SQL لا يثبت اكتمال الوظيفة.
- تصنيف «موجودة برمجيًا» يعني وجود واجهة/مسار؛ و«مرتبطة برمجيًا» يعني وجود استدعاء لمصدر بيانات في الكود؛ ولا يثبت أي منهما أن Migration طُبقت على Supabase الحي أو أن دورة العمل اختُبرت.
- لا تُحتسب الشاشة مكتملة تشغيليًا إلا بعد مراجعة دورة الاستخدام الفعلية، والصلاحيات، وحفظ البيانات، وسلامة الحسابات/الحركات، ثم الاختبار النهائي.
- لا تُنشأ بيئة Preview أو بيانات اختبار دائمة. التطوير على `main`، مع تأجيل الاختبارات الشاملة إلى نهاية دفعة التطوير.
- الحفاظ على بيانات المستخدم وعدم حذف أو إعادة إنشاء أي بيانات فعلية.

## 4. ملاحظات تقنية مؤكدة من قراءة الكود
1. شاشة التنقل الرئيسية تعرف 15 مجموعة رئيسية، وبها 485 ظهورًا لعناصر القوائم؛ لذلك يجب تنفيذ خريطة ربط لكل عنصر بدل الاعتماد على أسماء الوحدات فقط.
2. توجد سلسلة توجيه طويلة إلى شاشات متخصصة، لكن المسار النهائي لبعض العناصر غير المعالجة يفتح `_workspace()`؛ مساحة العمل العامة ليست بديلًا عن شاشة مالية أو مخزنية أو HR أو CRM متخصصة.
3. شاشة `ErpBusinessSuiteScreen` تقرأ سجلات النماذج غير التقريرّية من `erp_business_suite_records` بحسب الوحدة ونوع السجل، بينما تقرأ بعض التقارير مباشرة من جداول تشغيلية مثل الأصول والإنتاج والمشاريع والتذاكر. يجب إغلاق الفجوة بين إدخال النموذج العام والجداول التشغيلية قبل اعتماد هذه الوحدات.
4. شاشة الملخص التنفيذي ولوحة الموارد البشرية موجودتان في الكود، وتوجد ترحيلات حديثة للمؤشرات وأمان بيانات الموارد البشرية وخطط القوى العاملة؛ يلزم التأكد من تطبيق الترحيلات على المشروع الحي ومراجعة النتائج والصلاحيات.
5. Workflow التحقق الشامل أصبح يدوي التشغيل عبر `workflow_dispatch`، مع الاحتفاظ بخطوات التحليل واختبارات Flutter وبناء Web وWebView وAndroid APK. لا تُشغّل هذه الاختبارات أثناء كل دفعة تطوير.
6. عدد اختبارات Flutter الحالية 16 ملفًا فقط؛ لا يغطي ذلك تلقائيًا كل عناصر القوائم الـ468 ولا يثبت اكتمال CRUD أو دورة كل مستند.

## 5. قائمة التنفيذ ذات الأولوية

### P0 — ضبط خريطة الشاشات ومنع المسارات الوهمية
- [ ] استخراج كل عنصر قائمة وربطه بأحد التصنيفات: شاشة متخصصة، تقرير بمصدر، Business Suite، مساحة عمل عامة، تكامل خارجي، أو غير منفذ.
- [ ] تحديد كل العناصر التي تنتهي إلى `_workspace()`، وإقرار الشاشة المتخصصة أو التبويب المناسب لكل منها.
- [ ] إزالة الازدواج الوظيفي في قوائم الموارد البشرية/شئون الموظفين وعلاقات العملاء/خدمة العملاء دون كسر المسارات الحالية.
- [ ] تثبيت معايير الواجهة الموحدة لسلسلة: RTL، Tajawal، الألوان المعتمدة، ارتفاع 40px، مسافة 5px، اسم الحقل بجانب القيمة، وهيدر موبايل مدمج.

### P1 — البيانات الأساسية والربط
- [ ] مراجعة CRUD والصلاحيات وعزل `company_id` لكل من العملاء والموردين والأصناف والفئات والوحدات والفروع والمخازن ومراكز التكلفة والعملات والخزائن والحسابات والموظفين.
- [ ] التحقق من تسلسل التكويد التلقائي وسياسات الأكواد المركبة والجغرافية.
- [ ] مطابقة كل Repository مع الجداول والفهارس وRLS والقيود والزنادات ذات الصلة.
- [ ] جرد ترحيلات Supabase غير المطبقة على المشروع الحي؛ لا تُعاد كتابة أو تشغيل ترحيلات مدمرة دون مراجعة أثرها وبياناتها.

### P2 — الدورات التشغيلية الأساسية
- [ ] المشتريات: طلب ← أمر ← استلام ← فاتورة ← مرتجع ← سداد/كشف مورد.
- [ ] المبيعات: عرض ← أمر ← فاتورة ← تجهيز ← تسليم ← تحصيل/مرتجع.
- [ ] المخزون: إضافة/صرف/تحويل/جرد/تسوية/تكلفة/رصيد، مع منع الترحيل المكرر.
- [ ] المالية: سندات وقبض وصرف وتحويلات وشيكات وتسويات ومطابقة بنكية وقيود تلقائية.
- [ ] الموارد البشرية: ملف وعقد وتعيين وحضور وإجازة وسلفة وجزاء وتقييم ومسير وصرف راتب وتسوية نهاية خدمة.

### P3 — الوحدات المتخصصة والتقارير
- [ ] إكمال CRM وخدمة العملاء وSLA والزيارات والتصعيد.
- [ ] ربط الأصول والإهلاك والتصنيع والمقاولات بالجداول والقيود وحركات المخزون المتخصصة.
- [ ] ربط كل تقرير بمصدر ومعادلة موثقة، واختبار أرقام التقرير مقابل المستندات والحركات المصدرية.
- [ ] استكمال الفاتورة الإلكترونية والتكاملات الخارجية بعد توفر بيانات اعتماد فعلية.

### P4 — الاعتماد النهائي
- [ ] مراجعة الصلاحيات وRLS على الأدوار الفعلية.
- [ ] تشغيل اختبارات Python وFlutter Analyze وFlutter Test مرة واحدة في نهاية الدفعة.
- [ ] بناء Web والتحقق من ملفات البناء واختبار WebView لسطح المكتب والموبايل.
- [ ] بناء Android Debug APK والتحقق من وجود الملف وحجمه.
- [ ] إصلاح كل إخفاق وإعادة الاختبارات المتأثرة ثم اعتماد النشر.

## 6. طريقة قياس التقدم
لا توجد نسبة اكتمال إجمالية معتمدة في هذا الحصر؛ لأن عدد الملفات والقوائم لا يقيس سلامة الوظائف. سيُحدّث هذا السجل عند إغلاق كل بند مع رابط commit ودليل الربط أو التحقق. وتُفصل النسب مستقبلًا إلى:
- اكتمال الواجهات والمسارات.
- اكتمال الربط وقاعدة البيانات والصلاحيات.
- اكتمال الدورات التشغيلية.
- نتائج الاختبارات والبناء والنشر.
- الاعتمادات الخارجية التي تتطلب بيانات أو أجهزة أو حسابات حقيقية.

**الحالة عند إنشاء هذا السجل:** تم الحصر البرمجي الأولي؛ لم تُشغّل اختبارات، ولم تُعدّل بيانات Supabase، ولم يُجرَ أي حذف أو إنشاء بيانات تجريبية.
