# مواصفات فصل شاشتي سياسات البرنامج وسياسات الأكواد — سلسلة ERP
التاريخ: 2026-11-11
السبب: إعادة تثبيت قرار وجود شاشتين منفصلتين وعدم دمج شاشة «سياسات الأكواد» داخل «سياسات البرنامج».

## 1. الحالة الفعلية الحالية
- مجلد `lib/erp/screens` يحتوي `erp_program_policies_screen.dart` فقط لهذه الوظيفة؛ لا يوجد `ErpCodePoliciesScreen` مستقل.
- `ErpProgramPoliciesScreen` يحتوي tabs: الكل، برمجية، تكويدية، محاسبية، مخزنية، بيعية، شرائية، إدارية، الخطوط والألوان.
- السياسات ذات الفئة `تكويدية` موجودة داخل نفس الشاشة، ومنها `code_generation_registry` و`geo_code.*` و`customer_code` و`category_code.*` و`item_code`.
- Dashboard يوجه «سياسات البرنامج» إلى `ErpProgramPoliciesScreen` فقط؛ لا يوجد route مستقل لصفحة «سياسات الأكواد».
- لذلك الوضع الحالي لا يحقق قرار الفصل بين الشاشتين، حتى لو كان تبويب «تكويدية» ظاهرًا.

## 2. الفصل المطلوب

### الشاشة الأولى: سياسات البرنامج
Widget: `ErpProgramPoliciesScreen`
- تحتفظ بسياسات البرنامج العامة والتشغيلية.
- tabs: الكل، برمجية، محاسبية، مخزنية، بيعية، شرائية، إدارية، الخطوط والألوان.
- لا تعرض تبويب «تكويدية».
- لا تعرض إعدادات الأكواد ضمن الجدول العام ولا تكررها في شاشة أخرى.
- تشمل اسم البرنامج، الهوية، اللغة، الألوان، سياسات التشغيل والاعتماد والإعدادات العامة.

### الشاشة الثانية: سياسات الأكواد
Widget/route مستقل مقترح: `ErpCodePoliciesScreen`
- عنصر قائمة مستقل باسم «سياسات الأكواد» تحت إعدادات عامة/سياسات البرنامج، بجوار «سياسات البرنامج».
- يعرض جميع قواعد التكويد المركزية والهرمية في شاشة واحدة متخصصة.
- يحتفظ بتصميم Grid السابق: م، كود السياسة، بيانات السياسة، القيمة/الاختيار، تفعيل، الكل/مستخدمون، عدد المحددين (معاينة فقط).
- كل سياسة لها prefix إنجليزي 3 أحرف عند الحاجة، عدد خانات، parent digits/segments، تسلسل، composite/auto flags، preview.
- checkbox التفعيل دائري، وخانة التسلسل ثابتة وغير قابلة للإدخال اليدوي إذا كان المولد تلقائيًا.
- معاينة الكود فقط؛ لا تعرض أو تسمح بتحرير أكواد السجلات الموجودة.
- يوضح حالة السياسة: افتراضية/مفعلة/مقفلة لوجود بيانات/تحتاج مراجعة.

## 3. مجموعات سياسات الأكواد التي يجب أن تظهر
1. الدول وكود الدولة.
2. التقسيم الجغرافي: محافظة، مركز/حي، منطقة.
3. فئات الأصناف: رئيسية، فرعية، ثانوية.
4. الأصناف: Itm + مقاطع الفئات + البراند + التسلسل.
5. البراند/الماركة.
6. العملاء: Cus + كود المنطقة + تسلسل العميل.
7. الموردون.
8. وحدات الأصناف.
9. طرق الدفع.
10. المستخدمون وأنواع المستخدمين.
11. الفروع والمخازن ومراكز التكلفة والخزائن والحسابات.
12. الموظفون والوظائف والإدارات والعقود والرواتب عند وجود سياسة مستقلة.
13. الأصول والتصنيع والمقاولات والخدمة وCRM.
14. كل الكيانات الإضافية التي تستخدم `erp_assign_extended_central_code` أو `erp_assign_workspace_central_code`.

## 4. مصدر البيانات والتزامن
- لا تنشأ نسخة ثانية من سياسات الأكواد في جدول مستقل إذا كان `erp_program_policies` قادرًا على حفظها.
- يكون هناك مصدر حقيقة واحد لكل قيمة؛ لا تكتب UI قيمة في `erp_program_policies` ثم تحسب registry مختلفًا في Flutter.
- التصميم المفضل: user-facing policy rows في `erp_program_policies`، و`code_generation_registry` سجل داخلي مشتق/محدّث خادميًا، لا يظهر كمفتاح عادي ولا يسمح بتعديله مباشرة.
- أي تغيير سياسة يمر بتحقق server-side من عدم التكرار، والحد الأقصى، والـprefix uniqueness، ووجود السجلات الحالية.
- عند وجود سجلات تستخدم السياسة، تقفل الأجزاء التي ستؤدي لتغيير الأكواد، وتظهر سبب القفل ومعاينة التأثير.
- لا يُعاد توليد الأكواد الحالية بصمت؛ تغيير format يحتاج migration مخصصًا وسجل alias/history.

## 5. قرارات التكويد التي يجب تطبيقها داخل الشاشة المنفصلة
- كود الصنف الحالي في registry تسلسله 3؛ العقد المعتمد للمشروع يحتاج 2، ويجب توحيد UI/registry/trigger قبل الربط.
- بادئة المورد الحالية Ven؛ fallback في شاشة الأطراف Sup00001 يجب تصحيحه.
- سياسة الجغرافيا تعرض Con/Gov/Dis لكن trigger يستخدم country_code الرقمي وRig للمنطقة فقط؛ إما توضيح الواجهة أو تعديل المولد لتطبيق البادئات.
- معاينة الفئة الهرمية لا تستخدم `erp_preview_next_central_code(category)`؛ يلزم preview حسب parent.
- معاينة الصنف تحتاج RPC يحاكي الفئة الثانوية والبراند والتسلسل.
- معاينة العميل تستخدم `erp_preview_next_customer_geo_code` بعد اختيار المنطقة، ولا تستخدم المعاينة العامة Cus.

## 6. معايير الشاشة
- RTL، Tajawal، ألوان سلسلة المعتمدة.
- الحقول والصفوف وخيارات القوائم 40px، والتباعد 5px، والعنوان بجانب الحقل.
- لا scroll أفقي بين الصفوف؛ أي overflow يكون على مستوى Grid كامل مع بقاء رؤوس الأعمدة ثابتة.
- أزرار المهام السريعة التسعة وفق المعيار العام.
- كل تغيير يعرض Preview قبل الحفظ، وقفل السياسة يوضح سبب القفل.
- لا تحذف أو تعيد إنشاء policy rows القديمة دون ترحيل يحفظ القيم.

## 7. شروط الإغلاق
- route مستقل فعليًا لـ«سياسات الأكواد».
- «سياسات البرنامج» لا تحتوي tab «تكويدية».
- لا توجد مفاتيح تكويد مكررة أو مهجورة ظاهرة.
- جميع generators/previews/validators تقرأ مصدر الحقيقة نفسه.
- اختبار عدم تغيير الأكواد الحالية عند تعديل غير متعلق بالتكويد، واختبار تغيير السياسة بعد وجود بيانات.
- لم يتم تعديل Flutter أو SQL في هذه المرحلة؛ هذه مواصفة تصميم فقط.
