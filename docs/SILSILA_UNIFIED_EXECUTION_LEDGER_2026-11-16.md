## 4. قواعد الإغلاق
1. كل بند يربط بالملفات وSQL/RPC والجداول الفعلية.
2. لا تنشأ جداول أو migrations قبل فحص schema الحي وRLS والعلاقات وعدم تكرار الموجود.
3. لا تُقبل واجهة عامة بدل مستند متخصص متعدد البنود أو تقرير حسابي.
4. لا يُقبل نجاح `flutter analyze` أو build كبديل لاختبار الوظيفة.
5. اختبارات CI الأربعة مستقلة وواضحة: Android Release، Mobile/Flutter validation، Web App validation، Web Preview validation/deployment.
6. لا يُعلن APK قابل للتحديث قبل التحقق من applicationId وversionCode وشهادة التوقيع ومورد الأيقونة، ثم حفظ artifact. اختبار التثبيت/التحديث على جهاز فعلي يظل غير مثبت ما لم ينفذ على جهاز.
7. حالة كل بند واحدة من: مطلوب، قيد التنفيذ، جزئي، منفذ غير مختبر، متعطل، مكتمل مثبت.
8. لا يُعلن الإنجاز 100% إلا إذا كانت جميع البنود المطلوبة مكتمل مثبت ولا توجد حالات جزئي/متعطل/غير مختبر.
